# 知序 MVP · 产品方案

> 依据 `MVP使用(1).docx` 的三段式设想整理：**收集 → 知识库 → 思维导图**。
> 本文是产品与实现方案，网页原型在 `../app/`。

---

## 1. 一句话

**知序把「刷到的好内容」理成「自己的知识」：粘贴/分享小红书笔记 → AI 提炼成带来源的卡片 → 自动并入知识谱系 → 生成可互动、会合并重复观点的思维导图。**

不是另一个收藏夹，而是「收藏之后」的那一步。

---

## 2. 用户与场景

### 2.1 目标用户

- **主要**：18–30 岁、每天刷小红书 >30 分钟、有「收藏了就等于学了」习惯的学生 / 年轻职场人。
- **典型内容**：护肤经验、学习方法、职场表达、健身饮食、旅行攻略、存钱技巧。
- **次要**：需要把碎片内容整理成体系的内容创作者、考研/考公党。

### 2.2 核心场景（Job To Be Done）

| 场景 | 用户现在怎么做 | 痛点 |
|---|---|---|
| 刷到一篇很干的笔记 | 点收藏，或截图 | 收藏夹变成垃圾场，再也不会看 |
| 想找之前存过的某个方法 | 在收藏夹里翻关键词 | 只记得「好像刷到过」，找不到 |
| 同一主题刷到很多篇 | 每篇都存 | 观点重复、互相矛盾，不知道信谁 |
| 想回顾「最近学了什么」 | 没有回顾动作 | 只有输入，没有结构 |

### 2.3 价值主张

1. **省时间**：不要求用户写笔记，AI 从原文提炼；
2. **不丢来源**：每张卡片保留博主 / 链接 / 原句，可回原帖；
3. **越用越有结构**：新卡片优先并入已有谱系，放不下才新增大点；
4. **合并而不是堆叠**：思维导图自动合并重复观点，并说明「为什么合并、差在哪」。

---

## 3. 产品结构

```
知序
├── 01 收集
│   ├── 粘贴笔记文字（+ 可选链接）
│   ├── 「读取链接」：公开网页自动抓标题/描述/正文
│   ├── 手机 PWA Share Target：从小红书分享到知序
│   ├── QQ 分享收件箱：小号 + OneBot 桥投递链接
│   └── AI 提炼：标题 / 摘要 / 3–4 要点 / 标签 / 金句 / 来源
│   └── 人工确认：可改字段、可改分类，再保存
├── 02 知识库
│   ├── 知识谱系树：分类（大点）→ 主题（小点）→ 卡片
│   ├── 搜索 / 筛选 / 排序
│   ├── 卡片详情：摘要、要点、金句、来源
│   └── 导出 / 导入 JSON
└── 03 思维导图
    ├── 选知识大点 / 主题
    ├── 自动合并相似卡片（阈值可调）
    ├── 合并节点：来源、差异、合并原因
    ├── 点击节点：回看卡片
    └── 导出 SVG
```

### 3.1 收集页

输入方式有四种，按接入成本从低到高：

1. **粘贴文本**：最稳，任何平台都可用；
2. **粘贴链接 + 「读取链接」**：服务端抓公开网页的 `og:title/description` 和正文；
3. **PWA Share Target**：Android Chrome 安装知序后，从小红书分享 → 知序（`/share?url=...`）；
4. **QQ 分享收件箱**：用新 QQ 小号 + OneBot 桥，把链接私聊给机器人，知序收件箱出现待归档项。

链接能力的原则：

- 公开页面直接读取；**需要登录/反爬的平台（如小红书）读取失败时明确提示**，保留原链接，让用户粘贴文字；
- 链接只作为来源记录，不把整页 HTML 存进卡片；
- 服务端拒绝本机/内网地址（防 SSRF）；收件箱只监听本机，可加 token。

> QQ 接入涉及第三方协议与账号风控，必须用小号、自行扫码登录；知序不代替用户登录，详见 [03-链接分享与QQ接入.md](03-链接分享与QQ接入.md)。
- 解析过程分三步展示：读取原文 → 提炼卡片 → 匹配谱系，避免用户以为卡死。
- 解析结果必须**可编辑**：AI 给的是草稿，用户确认后才入库。
- 来源字段自动识别：小红书 / 微博 / 知乎 / B 站等域名，以及「作者：」；用户可改。

### 3.2 知识库页

- 结构：`分类（大点）→ 主题（小点）→ 卡片`。
- 新卡片归档规则：
  1. 先按内容判断分类（复用已有分类）；
  2. 在分类内匹配主题（同主题或高相似标签）；
  3. 匹配不到主题 → 新主题；
  4. 连分类都放不进 → 新建「新知识 · 关键词」大点。
- 树形交互是「文件夹点开」的隐喻，但底层不是文件夹，而是**内容关系**：移动/改名不应破坏卡片。
- MVP 不做拖拽改分类；用卡片详情里的「编辑」即可。

### 3.3 思维导图页

- 选择知识大点（或主题）→ 生成三层结构：大点 → 主题 → 卡片/合并节点。
- 合并逻辑：
  - 同一主题内的卡片先进入候选；
  - 计算相似度：`0.5×标签 Jaccard + 0.3×标题 bigram Jaccard + 0.2×摘要 bigram Jaccard + 0.3（同主题）+ 0.05（同分类）`；
  - 超过阈值（默认 0.45）合并；
  - 合并节点保留所有卡片：来源、每张卡片独有的要点（差异）、合并原因；
  - 阈值可调，用户能「看到 AI 的判断」而不是被黑箱合并。
- 交互：拖拽平移、滚轮缩放、点主题折叠/展开、点合并节点看差异、点卡片回看完整卡片、导出 SVG。

## 4. 数据模型

```ts
type Card = {
  id: string;
  title: string;            // ≤30 字
  summary: string;          // 80–120 字
  points: string[];         // 3–4 条可执行要点
  tags: string[];           // 3–5 个短标签
  category: string;         // 大点
  topic: string;            // 小点
  quote: string;            // 原文金句
  sourceLabel: string;      // 小红书 · @博主
  url?: string;             // 原帖链接
  createdAt: string;
  demo?: boolean;
};
```

- 分类、主题都是**字符串**，不是独立表；这样 MVP 可以纯前端跑，也方便用户改。
- 生产版再拆 `categories / topics / cards` 三表，加 `card_topics` 多对多（一张卡片可能属于多个主题）。
- 保留 `source` 与 `quote` 是「可信」的底线：AI 摘要可以改，来源不能丢。

## 5. AI 管线

### 5.1 MVP（当前网页）

- 有 `server.py` + key：调用星火（OpenAI 兼容）输出严格 JSON；
- 没有 key / 直接打开 HTML：本地规则提炼（关键词分类 + 抽取式摘要 + 要点排序），保证可演示。

### 5.2 生产建议

1. **解析**：正文清洗（去 emoji/话题标签/水印话术）→ 分句；
2. **卡片化**：LLM 输出 JSON（标题/摘要/要点/标签/分类/主题/金句），带原文引用；
3. **分类**：先用规则/embedding 召回候选分类，再让 LLM 在候选里选，减少乱造分类；
4. **主题**：同分类内用 embedding 聚类 + LLM 命名；
5. **合并**：embedding 相似度召回候选对，LLM 判断「是否同一观点、差异是什么」，避免只靠字符相似度；
6. **质检**：要点必须能在原文找到依据；找不到就标「AI 推断」或不展示。

### 5.3 为什么不让 AI 直接生成整棵知识树

- 生成整棵树不可控、不可解释，用户无法纠正；
- 逐步归档 + 可视化谱系，用户能看见「为什么放这里」，也能改；
- 合并必须可解释，否则用户不敢信。

## 6. MVP 边界

### 做

- 粘贴文本 → 提炼卡片 → 编辑 → 保存；
- 自动分类 / 主题 / 来源；
- 树形知识库、搜索、删除、导入导出；
- 合并式思维导图、阈值、差异、来源、SVG 导出；
- 本地持久化；可选接真 AI。

### 暂不做（明确延后）

- 直接抓取需要登录/反爬的小红书正文（合规/稳定性风险；已提供分享文本/剪贴板/PWA/QQ 等绕行方式）；
- 登录、多端同步、协作；
- 图片/视频内容理解；
- 间隔重复复习、学习统计；
- 浏览器插件 / 分享面板；
- 移动 App（先用响应式网页）。

## 7. 指标

| 指标 | 定义 | MVP 目标 |
|---|---|---|
| 激活率 | 首次访问 → 保存第一张卡片 | ≥ 35% |
| 卡片产出 | 每人每周新增卡片 | ≥ 5 张 |
| 回访率 | 7 日内再次打开 | ≥ 25% |
| 提炼采纳率 | AI 草稿未大改直接保存 | ≥ 60% |
| 合并接受率 | 合并节点被点开、未手动拆分 | ≥ 50% |
| 来源保留率 | 带 sourceLabel 的卡片占比 | 100% |

---

## 8. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 平台条款 / 版权 | 抓取或整篇存储小红书内容有风险 | 只处理用户主动粘贴的文本；不抓取；卡片是摘要 + 短引用；保留来源 |
| AI 编造 | 摘要/要点可能过度推断 | 要点必须可在原文定位；保留金句；用户可编辑 |
| 合并过度 | 不同观点被合并 | 阈值可调；展示差异与来源；不做不可逆删除 |
| 分类膨胀 | 新分类越来越多 | 优先复用；新分类需用户确认；定期清理 |
| 隐私 | 笔记可能含个人信息 | 数据默认只存本地；导出由用户控制；生产版明确隐私政策 |
| 链接失效 | 原帖删除 | 保留标题/博主/金句；可选快照（后续） |

## 9. 路线图

- **M1（本原型）**：收集 / 知识库 / 思维导图 + 本地演示 + 可选真 AI。
- **M2**：链接读取（公开网页已做）、PWA 分享目标（已做）、QQ 收件箱（已做原型）、浏览器插件、批量导入、卡片编辑。
- **M3**：复习（间隔重复）、搜索语义化、相似卡片推荐。
- **M4**：多端同步、账号、导出 Markdown/Notion。
- **M5**：主题自动聚类、跨分类关联、AI 问答（基于自己的卡片）。

---

## 10. 技术选择

- 原型：原生 HTML/CSS/JS，零构建、零依赖，双击 `index.html` 就能用；localStorage 持久化。
- 可选服务：`server.py`（Python 标准库）做静态服务 + `/api/analyze` 代理，key 只在服务端。
- 生产：Next.js / React + FastAPI + Postgres（pgvector）；卡片表 + 向量表；LLM 走统一网关；任务队列做解析与合并。
- 不选重型框架做 MVP 的原因：验证的是产品逻辑，不是基础设施；先让 3 个页面跑通，再谈扩展。
